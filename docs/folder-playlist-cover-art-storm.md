# 폴더 재생목록을 열면 앱이 멈추던 문제 — 조사 기록 (2026-08-14)

## 한 줄 요약
재생목록을 그릴 때 **모든 트랙의 앨범 아트를 한꺼번에** 요청해, 351곡짜리 폴더에서
**ffmpeg 프로세스 351개가 동시에** 떴다. 게임 OST라 아트가 하나도 없어 전부 실패했고,
"아트 없음" 기록이 메모리에만 남아 **앱을 켤 때마다 같은 일이 반복**됐다.

영향 버전: **1.4.9** (폴더 재생목록이 처음 들어간 버전) / 수정: **1.4.10**

---

## 1. 증상

> "어제 로컬 폴더 재생 잘 됐는데 오늘 다시 앱을 켜서 저장된 재생목록에 접근하려고 하니
> 렉이 엄청 걸리고 노래가 안떠."

어제(추가 직후)는 멀쩡했고 오늘(재실행 후)만 문제라는 점이 단서였다.

## 2. 확인한 사실

`%APPDATA%\youtube-player\playlists.json`:

```
folder  "Latale_OST"  tracks=351  …\OneDrive\Music\Latale_OST
```

`%APPDATA%\youtube-player\covers\` — **파일 0개.**

커버 캐시가 비어 있다는 건 351번의 추출이 **한 번도 성공하지 못했다**는 뜻이다.
실제로 폴더의 mp3 하나로 확인:

```
ffmpeg -y -i "001. [메인테마] MAY be happy.mp3" -an -update 1 -frames:v 1 out.jpg
→ Output file does not contain any stream   (실패, 1.5초 소요)
```

옛날 게임 OST라 **어떤 파일에도 커버가 내장돼 있지 않았다.**

### OneDrive는 원인이 아니었다
경로가 OneDrive 안이라 클라우드 전용 파일(재생할 때마다 재다운로드)을 의심했지만,
파일 특성을 보니 `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`(0x400000)가 353개 전부 **0**,
대신 `PINNED`(0x80000)가 켜져 있었다 — 즉 **이미 로컬에 내려받아 고정된 상태**였다.

## 3. 원인

`renderQueue()`는 큐를 다시 그릴 때마다 폴더 트랙 **전부**에 대해
`ipcRenderer.invoke('local-cover', …)`를 걸었다. 메인 프로세스의 핸들러는
요청이 오는 족족 `execFile(ffmpeg …)`를 실행했으므로, 목록을 한 번 그리는 것이
**프로세스 351개를 동시에 띄우는 일**이 됐다.

세 가지가 겹쳐 최악이 됐다.

1. **커버가 없는 파일은 판정 자체가 비싸다.** 아트가 있으면 헤더 근처에서 끝나지만,
   없으면 ffmpeg가 파일을 끝까지 훑고 나서야 "스트림 없음"으로 실패한다.
2. **실패는 캐시에 남지 않는다.** 성공하면 `covers/<hash>.jpg`가 디스크에 남지만,
   실패 기록(`coverMisses`)은 **메모리 Set**이었다. 앱을 끄면 사라지므로 매 실행마다
   351곡을 다시 확인했다.
3. **중복 요청이 합쳐지지 않았다.** 실행 직후에는 재생 위치 복원 → 재생목록 자동 갱신 →
   목록 열기로 `renderQueue()`가 여러 번 돈다. 렌더러 캐시는 결과가 **돌아온 뒤에만**
   채워지므로, 아직 진행 중인 요청은 걸러지지 않고 그대로 또 351개가 쌓였다.

어제 괜찮았던 이유도 여기서 나온다. 폴더를 막 추가한 직후에는 곡을 바로 재생했지만,
오늘은 앱을 켜자마자 351곡짜리 목록이 복원되면서 폭주가 시작됐다.

## 4. 수정

- **보이는 줄만 추출** — 큐 목록에 `IntersectionObserver`를 걸어 화면에 들어온 행만
  커버를 요청한다. 재생목록을 접어두면 스크롤 박스 높이가 0이라 **아무것도 실행되지 않는다.**
- **동시 실행 2개 제한** — 메인 프로세스에 세마포어를 둬 ffmpeg가 2개를 넘지 않는다.
- **실패를 디스크에 기록** — `covers/<hash>.none`에 파일의 `mtime:size`를 적는다.
  다음 실행부터는 확인 없이 건너뛰고, 파일이 교체되면 스탬프가 달라져 다시 확인한다.
  성공한 이미지도 같은 스탬프로 무효화한다.
- **중복 요청 병합** — 렌더러는 결과 대신 **Promise**를 캐시하고, 메인 프로세스도
  같은 파일에 대한 추출을 하나로 묶는다.

## 5. 검증

문제의 폴더로 직접 측정했다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 목록 열 때 동시 ffmpeg | 351 | **최대 2** |
| 20곡 처리 시간 | — | **406 ms** |
| 같은 20곡 재요청 | 매번 전량 재실행 | **13 ms, ffmpeg 실행 0회** |
| 앱 실행 시 커버 시도 | 351곡 | **화면에 보인 7곡** |

## 6. 교훈

- "요청당 프로세스 하나"는 목록 UI에서 **항목 수만큼 곱해진다.** 렌더 경로에서 외부
  프로세스를 띄운다면 동시 실행 제한은 선택이 아니라 필수다.
- **비싼 실패는 성공만큼 캐시해야 한다.** 없는 것을 확인하는 비용이 있는 것을 읽는 비용보다
  클 수 있고, 그 결과가 뒤집힐 일도 거의 없다.
- 인메모리 캐시는 "한 세션 안에서만" 유효하다. 매 실행 반복되는 작업이라면 디스크로 내려야 한다.
- 목록 항목의 부수 작업은 **화면에 보일 때까지 미룬다.** 351곡 중 사용자가 실제로 보는 건
  한 화면뿐이다.
